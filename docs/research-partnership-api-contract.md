# Research partnerships contract · 1.0.0

U1 shared contract for U2–U5 of [the continuation plan](plans/2026-10-18-research-partnerships-continuation.md). The authoritative machine vocabulary is `app/lib/research-partnership-core.js`: CommonJS or browser `SBE_RESEARCH_PARTNERSHIPS`. All exported metadata, nested fields, enums, presets and operation descriptions are deeply frozen. This module performs no persistence, authentication, provider calls or legal execution.

## Transport and identity

Extend the existing `POST /api/research` JSON transport with `{token,action,...payload}`. Select the fixed service-only `research_partnership_rpc` only for this module's allowlisted actions; reuse the existing verified credentials, `research_private` authorization, row-locked current study membership, current owner password version and RLS. Existing research operations and participant invitations remain separate. Never accept client `owner`, `actor`, `role`, permission context, execution status or provider evidence as authority.

Every action except `READ_ACTIONS` requires a UUID `requestId`. Receipts bind actual actor, study, action and canonical payload; replay with changed payload is `409 conflict`. `workspaceAnalysis` is a mutation because it persists a source snapshot and result. Audited reads remain reads. Existing record mutations require `expectedRevision` equal to the head revision; new records use `null`. Missing/inaccessible scopes have the same `404 not_found`. Invalid input is `400 invalid`, expired/revoked authority `403 unauthorized`, stale revision `409 conflict`, missing dependency `503 not_configured`. Errors contain safe codes and fixed Hebrew messages only.

Success follows the existing envelope `{ok:true,status:200,...result}`; failures `{ok:false,status,error}`. All private responses/downloads use `Cache-Control: private, no-store`, `Vary: Origin`. Browser storage holds only the existing authentication token, never partner profiles, drafts, findings, documents or provider sessions. Scope/account changes clear private DOM and invalidate pending requests through the existing client lifecycle.

## Typed data and common shapes

`RECORD_SCHEMAS[kind].fields` is the exact allowed field list. Each descriptor has `{id,label,type,required?,section?,choices?,fields?,reference?,category?,maxLength?}`. Labels are Hebrew. Types are `text`, `email`, UUID `id`, ISO `date`, canonical decimal `money`, nonnegative safe `integer`, `boolean`, `enum`, unique string `tags` and typed object `rows`. `tags` with `itemType:'id'` contains UUIDs. Row descriptors recursively declare every permitted key. Unknown keys, wrong types, arbitrary JSON, invalid references, impossible dates and reversed date ranges fail with `safeError('invalid')` without echoing input. `reference` identifies the target kind, not permission to access it.

Money is a nonnegative canonical decimal **string with exactly two fractional digits**, e.g. `"0.00"`, `"125.25"`; at most twelve integer digits, no leading zeros except zero itself, no exponent, number coercion or silent rounding. Currency choices are ILS/USD/EUR/GBP. Text is bounded to 20,000 characters by default (titles 240), emails 254, tags/rows 200 elements, tag text 500. Blank strings may remain in drafts; required completion rejects them. Optional fields are omitted rather than `null`. `validateRecord(kind,data,{complete})` returns a validated copy; `missingFields(kind,data,extraRequiredIds)` returns exact field paths, including row cells. `validatePartner` and `validateApprovedTerms` enforce their separately exported field descriptors.

Database references always resolve transactionally within the same study and authorized partner scope. A guessed valid UUID is not authorization. Document, template, instrument/consent version, snapshot, contribution, budget, amendment and other nested references repeat these checks. A record viewer gains no rights to the rest of the researcher's folder or referenced documents.

Server-created result types:

- `PartnerData`: keys from `PARTNER_FIELDS`. `Partner`: `{id,revision,profile,createdAt,updatedAt}`. `PartnerSummary`: `{id,revision,fullName,institution}`. Never return the individual code or a global credential key. Owner may bind an existing individual code; self-save resolves identity exclusively from the verified session.
- `StudySummary`: existing authorized `{id,title,status,permissions}` projection. `WorkspaceSummary`: `{studyId,partnerId,studyTitle,partnerName,recordCounts,pendingCount,deadlines,records,documents?,snapshots?,partnershipActive?}`; each record is a permitted `RecordSummary`. Optional document/snapshot metadata remains folder-authorized. Counts, search and deadlines apply the same record authorization before aggregation. `RecordSummary`: `{id,partnerId,kind,status,revision,title,updatedAt,headVersionId}`. Explicitly released records may appear in a viewer's own workspace with their original partnerId for exact record requests; this grants no source-folder profile, siblings, counts or history access. Contractual partnershipActive is derived only from verified execution and applicable active study, ethics and consent conditions.
- `Record`: `{id,studyId,partnerId,kind,status,revision,headVersionId,approvedVersionId,publishedVersionId,createdAt,updatedAt,binding}`. `binding` is server-derived, false for proposals, application approvals, budgets and unsigned agreements. Optional unavailable pointers are null. `RecordVersion`: `{id,recordId,studyId,partnerId,number,data,contentHash,createdAt,proposedBy,submittedAt}`; `proposedBy` is a study-scoped actor label/ID, never a credential key. Version summary omits data and retains `{id,number,contentHash,createdAt,proposedBy,submittedAt}`.
- `Review`: `{id,recordId,versionId,decision,note,reviewedAt,reviewedBy,approvedTerms,cancellationAgreementVersionId}`. Contribution `approvedTerms` uses `APPROVED_TERMS_FIELDS`, is stored separately from original requested terms, and remains nonbinding until included in a verified executed agreement. Other reviews omit it.
- `Publication`: `{id,recordId,versionId,viewerPartnerIds,downloadPartnerIds,publishedAt,withdrawnAt}`. Download partners must be a subset of viewers. Viewers receive only their own effective access, not a list of other viewers. `FindingComment`: `{id,recordId,versionId,text,authorLabel,createdAt}`; only current authorized published viewers with comment permission can comment/read authorized comments.
- `Readiness`: `{signing,approvedTemplate,ipExplanation,mail,googleForms,impactAI}`, each `{configured:boolean,state:'ready'|'not_configured'|'blocked',message:string}`. Report actual configured dependencies; never return credentials/provider payloads. Missing approved text and signing provider remain `not_configured`.
- `PrivateDocumentMetadata`: `{id,studyId,partnerId,recordId,filename,mediaType,size,sha256,createdAt}`. Private encrypted bytes remain separate from record JSON; only an authorized exact document read/export returns bytes. No public URL. Content-free audit stores IDs, operation and outcome only.

The following are payloads besides common `token`, `action`, and mutation `requestId`. `scope` means **all** `{studyId,partnerId,recordId}`; `rev` means `expectedRevision`. UUIDs/arrays/enums follow `OPERATIONS` and schema descriptors. Reads are exactly `READ_ACTIONS`.

`PartnerInvitation`: `{id,studyId,partnerId,revision,status,expiresAt,createdAt,acceptedAt,revokedAt,preset,permissions}` where status is `pending|accepted|revoked|expired`. Raw opaque token is returned only at creation when needed for delivery; store only its digest. Default expiry is server 30 days; owner may choose an earlier valid expiry. `PartnerInvitationPreview`: `{id,studyId,partnerId,studyTitle,expiresAt,preset,permissions}`. An invite never becomes a login credential or participant consent. `DeliveryState`: `{configured,status:'not_configured'|'queued'|'accepted'|'failed'|'unknown'}` reports actual mail infrastructure, not invented delivery.

`AgreementApproval`: `{id,recordId,versionId,documentHash,party:'owner'|'partner',ipExplanationVersionId,ipReadAcknowledgedAt,approvedAt}`. Caller cannot nominate a party. `SigningSession`: `{id,recordId,versionId,documentHash,state,configured,embeddedUrl,expiresAt,completedAt}`; state `not_configured|awaiting_signers|in_progress|completed|declined|expired|failed`; embedded URL is short-lived, provider-bound and only for the actual requesting party. `completed` is returned only after server verification. No browser-supplied URL, signature evidence or completion state is accepted.

`signatureComplete` is internal only, never in public `CLIENT_ACTIONS`. Trusted adapter payload: `{studyId,partnerId,recordId,signingId,versionId,documentHash,providerEventId,finalDocumentId,finalDocumentHash,auditCertificateDocumentId,verifiedSigners,completedAt}`. The adapter authenticates the provider event, retrieves final evidence server-side, matches both signer identities/authority and explicit consent to the same approved version/hash, checks event idempotency and records immutable evidence. Return `{record,signing}`. A callback body claiming these fields is not verification; missing approved provider/credentials/authority policy prevents execution and partnership activation.

`AnalysisOperation` is exactly `descriptive|frequency|comparison|trend`; no SQL or arbitrary expressions. Parameters come from the approved typed request (`questions,variables,comparisons,timePoints,requestedOutputs`) and current allowed study fields. On omission of `sourceSnapshotId`, SQL creates an immutable same-study consent-bound source snapshot and provenance manifest. A supplied snapshot must already be same-scope and usable under current consent. `AnalysisProvenance`: `{sourceSnapshotId,requestRecordId,requestVersionId,operation,analysisVersion,consentProtocolVersionId,questionnaireVersionIds,toolVersion,createdAt}`; unavailable fields are explicitly null, never guessed. `ApprovedAnalysisProjection`: `{count,variables,results}` uses fixed operation result schemas and owner-approved eligible source rows. The new `analysis_result` is **draft**, with server-populated source/method/version/summary; owner privacy/consent review and release are separate. The operation never auto-publishes a finding.

`ImpactAIState`: `{configured,state:'not_requested'|'not_configured'|'ready'|'failed',summary:null|string}`. Exact `changes` do not depend on AI. No configured model or successful generation means no invented summary. AI output cannot approve, execute or confer rights.

## Versions, status and obligations

Record kinds are exactly application, analysis_request, analysis_result, finding, contribution, agreement, agreement_template, budget, obligation, decision. Documents are separate binary objects. `RECORD_STATUSES` and `RECORD_TRANSITIONS` define exact status/action/authority combinations. Roles are presentation presets, not authority. SQL validates the transition and actual record identity in the committing transaction.

Applications, analysis requests, budgets and decisions use `draft → submitted → under_review → approved|rejected|changes_requested`, with changes requested resubmitted. Direct submitted→approved/rejected/changes_requested is also allowed. Contributions add approved→completed and have exactly eight categories: scientific, methodological, questionnaires, educational_content, technology, funding, professional_services, other. Requested recognition/compensation/usage/IP/owner obligations and all original proposal versions remain intact; owner review retains proposed agreed terms separately. Approval never creates a financial obligation.

Findings use `draft → owner_review → approved → published → withdrawn`; owner may return owner_review to draft. Analysis results use the same stages, with release/withdrawal through owner `recordReview`. Exact approved version, source snapshot, method/analysis/tool/questionnaire/consent provenance and documented privacy/consent review precede release. `findingPublish` alone sets explicit viewers/downloaders. Source changes do not alter a publication pointer. A published finding must be withdrawn before saving a replacement draft. A viewer cannot discover an unpublished head or earlier private history.

Every save appends an immutable version, including drafts; it never overwrites submitted data. New counterproposals are allowed on unexecuted records and reset the head to draft, invalidate all prior approvals and preserve proposer attribution. Author and owner can negotiate agreement revisions. Executed agreement content/evidence cannot be saved over; `agreementAmend` creates a new linked record requiring fresh mutual approval/signatures. Publication authorization always resolves the exact published version rather than whichever head is newest.

Agreements add `approved → signing → executed`. Owner review approval permits mutual final-version approval; it is distinct from both parties' `agreementApprove` receipts and provider execution. Both parties must approve the identical immutable version/hash. Any new version invalidates approvals and an old signing session cannot execute the replacement. IP reading acknowledgement is distinct from signing consent and signature. An approved checkbox is never execution. Template stages are draft→approved→retired; approved versions remain immutable references.

Obligation stages are draft→under_review→approved→in_progress/completed/disputed/cancelled as enumerated in `RECORD_TRANSITIONS`. Each obligation retains executed agreement ID/version/hash, clause reference, party, amount/currency/deadline and evidence. Owner review is needed before tracking. Editing progress/evidence cannot change signed terms; altering money/deadlines/rights needs a new executed amendment and linked obligation. Cancellation review requires `cancellationAgreementVersionId` resolving to a verified executed amendment authorizing that cancellation, not an owner checkbox.

`isBindingObligation` only interprets **trusted server output** containing `{kind:'obligation',sourceAgreementStatus:'executed',sourceAgreementVersionId,sourceAgreementHash,providerVerification:'verified',ownerReviewed:true}`. It cannot turn client JSON into execution evidence. SQL derives these fields from verified immutable provider execution and owner extraction review; record data cannot supply them. No unsigned proposal, approved contribution, budget or unsigned amendment is binding.

## Agreements and exports

Twelve agreement sections are parties, study, tools, contributions, sharedExpenses, professionalFees, development, mutualIP, privacyEthics, durationTermination, annexes, reviewSigning. Their Hebrew labels, all fillable fields, expense rows, service-fee rows, milestones and custom clauses are in `RECORD_SCHEMAS.agreement`. Reuse approved same-scope profile/study/contribution/budget/tool references; an authorized override creates a new proposal value and version.

`agreement_template` stores owner-supplied title, templateVersion, explanationVersion, twelve `{sectionId,text}` clauses, ipExplanation, mutualIPClause and requiredFieldIds. Approval is owner-only, exact immutable version. No legal clauses are built in. `{{fieldId}}` placeholders refer only to known top-level agreement fields; unknown/malformed placeholders, unknown required IDs, duplicate/missing complete sections fail validation. Approved legal text/IP explanation have not been supplied in this clone; no claim is made to have mapped an unseen Word file.

`renderAgreement(data,templateData)` returns deterministic `{direction:'rtl',lang:'he',title,templateVersion,explanationVersion,sections,ipExplanation,missingFields,dependency,ready,text}`. Without template, render field values and honest `approved_template_missing`; no generated substitute legal text. Missing required or placeholder values are named in Hebrew and `ready:false`. Render data is plain text, never trusted HTML; browser uses textContent and export HTML escapes every text value. Mixed Hebrew/English/dates/numbers remain exact. `compareRecords` returns ordered `{path,fieldId,label,category,before,after}` with nested row cells and exact values; categories include financial, deadline, IP, access, privacy, obligations and content.

Version content hashes use SHA-256 of canonical typed data (recursive object keys sorted, array order preserved, UTF-8, no Unicode normalization or number coercion). Mutual approval `documentHash` equals the agreement version's `contentHash`; the typed agreement includes exact immutable approved template and IP-explanation version references. Signing additionally binds the generated provider document bytes to that approved version, records their independent hash and retains the executed bytes' `finalDocumentHash`. An export hash is the SHA-256 of that export's bytes and is not an interchangeable format's signature hash. Never present the canonical agreement hash as the PDF integrity hash.

Exports support UTF-8 text, typed JSON, escaped RTL HTML, and actual OOXML DOCX. PDF is supported through authorized exact-version HTML and the existing `SBE_DOC` browser print-to-PDF path (A4, 24mm margins, RTL). No server PDF/font runtime dependency is introduced, and preview/download does not require signing. Unsupported optional exporters must report actual configuration, never return HTML renamed DOCX/PDF. Current authorization and consent are repeated before every export/download; separate finding downloads and dataset exports require their explicit grants.

## Permission defaults and local evidence

New `researcher` preset is `[view_study,view_approved_findings]`. Collaborative analysis adds propose_analysis, view_analysis_results, comment_on_findings. Neither grants raw rows, identities, content, approved pseudonymized data, dataset export or finding downloads. Existing explicitly assigned grants and existing PI/assistant presets remain unchanged. `manage_study_questionnaires` maps to existing manage_questionnaires, without introducing a duplicate raw-data right. Permission grants alone do not bypass record viewers, study membership, individual folder scope, consent or ethics.

Focused proof-first tests observed the expected missing-module failure before implementation; a second RED caught workspaceAnalysis incorrectly classified as read before its snapshot contract was corrected. Current focused suite covers frozen browser/CommonJS API, presets, typed/nested validation, money/dates/references, all 12 sections, template completion/placeholders, RTL preview, exact implications, transitions and nonbinding proposals. The core is standalone; existing base core/client/migrations are unchanged in U1. Database transactions, backend/provider adapters, UI forms, native Word/HTML exports and browser verification belong to U2–U5. Operational legal templates, signing provider, real email/Google configuration and production changes remain external prerequisites.
