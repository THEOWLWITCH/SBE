# BE GOOD research implementation contract · 1.0.0

This is the shared implementation interface for U2–U5 of the approved research plan. It implements the request in `docs/requirements/2026-10-13-communication-research-requirements.md`; it does not authorize production migration, email dispatch or deployment. The existing educational `/api/studies` library is unrelated and unchanged.

## Common boundaries

Browser requests: `POST /api/research`, JSON `{token, action, ...payload}`. Use the existing personal/system session, not a client actor/owner/role assertion. Responses: `[status, out]` from the handler; HTTP JSON `{ok: status < 400, status, ...out}`. All success, failure and download responses use `Cache-Control: private, no-store` and `Vary: Origin`. No browser research local/session storage. Existing session storage contains only the existing auth session.

Store factory: `supabaseResearchStore(url, key, {fetchImpl, timeoutMs} = {})`, returning `{rpc(token, action, payload)}`. One fixed POST to `/rest/v1/rpc/research_rpc`, body `{p_token: token, p_action: action, p_payload: payload}`. Return its JSON object. SQL errors represented as `{error, status}` are raised as `ResearchStoreError` with `.status` and `.code`; safe codes only. Transport/provider text is not sent to browsers. Legacy JWT service keys use apikey and bearer headers; opaque `sb_secret_` keys use apikey only. No privileged key in the browser. No generic relation/column operation.

Backend entry: `handleResearch(accessStore, researchStore, body, options = {})` → `[status, out]`. Options include `now`, `contactKey` (32-byte base64 AES key), `siteOrigin`, `resolveGeneratedSample`, and mail configuration/dependencies. Validate and project client fields before calling the store. Database authorization remains authoritative and repeats current credentials, rights, state and consent inside the committing transaction. The backend rejects internal actions from browser requests. No field named actor, owner, role, permission context, global user ID, ciphertext, mail token digest or verified provenance can be supplied as an authority by a client.

Every mutation requires `requestId` (UUID). Study edits/status/member/form changes require `expectedRevision` (nonnegative integer). Receipts are scoped to the actual actor, study and action; a reused request ID with another payload returns conflict. Study revision changes serialize on the study row. New IDs are server/database generated UUIDs. Nonexistent and inaccessible IDs return the same 404 `not_found`; invalid auth returns 403 `unauthorized`; invalid input 400 `invalid`; stale revision/consent 409 `conflict` / `consent_changed`; rate limit 429 `rate_limited`; missing configuration 503 `not_configured`. Errors contain no foreign names, counts, email, text or SQL.

Shared UMD `app/lib/research-core.js` is the exact action/permission/status vocabulary. UI `hasPermission` only controls presentation. SQL and backend explicitly check the same named rights. Role presets are starting suggestions; roles do not implicitly confer permissions. Research release/application 1.2.0, research API 1.0.0, schema 1, metrics 1.0.0. Communication tool 1.2.0; unchanged engine/prompt 1.1.1 and principles 18-1.0.0 remain distinct historical fields.

## Study shape and activation

Study: `{id, revision, status, config, permissions, versions, stats, createdAt, updatedAt}`. `config` fields:

- `title`, `description`, `researchQuestions` (string array), `principalInvestigator` (label), `population` (description), `eligibleInstitutions` (existing institution-name array; empty means any valid personal educator code).
- `startDate`, `endDate` (ISO dates), `approvals: {status: 'pending'|'approved', reference, documentation}` (owner supplied textual documentation/reference; no external document fetch).
- `consentVersionId`, `instrumentVersionIds` (UUID array), `schedule` (array of `{waveId, instrumentVersionId, offsetDays, reminderDays}`; wave IDs are unique strings; reminderDays is an array of positive day offsets after the wave, empty means no reminders).
- `dataCategories`, `exportCategories` (subset of shared categories); `retentionDays` (positive integer), `withdrawalPolicy: 'erase'|'retain-consented'`.
- `contactKinds` (subset of followup, feedback, update), `expectations` (participant-facing explanation).

Partial drafts are allowed. Only owner can create, approve active/reactivated state, pause, complete, archive and run retention/reconcile unknown mail. Owner-confirmed activation requires title, population, questions, approved documented approvals, valid start/end range, retention/withdrawal policy, a published same-study consent with disclosure matching categories/contact policy, published same-study scheduled instruments, schedule/category validity. A changed collection scope requires a new consent version; existing participants never acquire its additional grants automatically. Config revisions are immutable history; current study row is a pointer/status, not historical record replacement.

Statuses: draft → pending_approval → active ↔ paused → completed → archived. Owner may return pending_approval to draft. Reactivating a paused study repeats activation confirmation/checks. Completed/archived cannot collect. Draft and pending_approval cannot enroll or send research mail.

`consents` is `{participate: true, surveys: boolean, usage: boolean, historical: boolean, generated: boolean}`; optional categories unchecked by default. Published consent definition is `{title, text, categories, contactKinds, retentionDays, withdrawalPolicy, expectations}` and must match activated config. `preferences` is `{followup, feedback, update}` booleans. Verification and welcome are necessary enrollment communications, not bulk marketing. If new consent is published/activated, capture and follow-ups stop until explicit reconsent; the participant portal explains recovery. Withdrawal and preferences remain possible when the study is paused/completed, but expired/revoked login requires recovery through the existing personal-code flow/owner.

Instrument definition: `{title, construct, validationStatus: 'under-development'|'study-approved', description, items}`. Item: `{id, type, label, required, options?, min?, max?}`. Options are unique strings, bounded arrays. Allowed types are shared ITEM_TYPES. Never fabricate PLSE/WIFP items, validity or a combined score. Form builder may start blank and label the construct under development. SQL also rejects unknown item keys, answers/types/ranges/options and foreign/unscheduled versions. Numeric aggregate summaries are item-level descriptive counts/means only, not psychological scores. Records retain approved definition IDs, study config revision, exact consent and application/tool/engine/prompt/principles/model/schema versions available for that observation; unavailable model/source fields are explicitly null, never guessed.

Member delegation: owner alone sets `delegablePermissions`. Nonowner manager may assign/remove only other nonowner collaborators within their owner's explicit delegation envelope, cannot edit self/owner membership, cannot add a permission absent from envelope or set another delegation envelope. Codes must resolve to existing live individual staff/instadmin records. No global identity search. Membership lists only available to manage_researchers, not general study viewers.

## Database/security requirements

New private `research_private` schema: studies, immutable study_versions, memberships, form_versions, participants, consent_history, contacts, verification_tokens, responses, historical_samples, generated_samples, usage_events, invites, outbox, audit_events, request_receipts (or equivalent relational separation). All study children carry `study_id`; participant/form/sample references have composite study foreign keys. Participant IDs are independent random UUIDs per study. Never expose global credential keys, cross-study document IDs, email hashes or identities in pseudonymous projections.

New restricted NOLOGIN NOSUPERUSER NOBYPASSRLS worker role is not any table owner. Fixed private SECURITY DEFINER dispatcher owned by that role, explicit `search_path = ''`, qualified names and tightly limited ACL. Public `research_rpc` is SECURITY INVOKER callable only by service_role. No direct new schema/table privileges for anon/authenticated/service_role, regardless of BYPASSRLS. RLS ENABLED/FORCED on study data; missing/foreign context denies. Separate migration-owner role owns tables/functions that require ownership; worker receives only needed table rights. Do not change unrelated production auth/table privileges.

The dispatcher verifies the raw existing token using pgcrypto HMAC and existing `public.access_settings` token-secret plus current code/institution records. HMAC key is UTF8 text of secret, not hex decoding. Payload exp is milliseconds. Owner is ONLY verified k=sys. Personal k=code requires current matching kind/inst and live nonrevoked nonexpired staff/instadmin record, active institution/subscription+configured grace. Shared inst/open/course/student/LEGACY sessions are excluded. Credential/auth rows, applicable membership, study, participant/consent are locked before protected operations; commit-time state revocation and serialization are enforced. Reset transaction-local actor/study/permissions context for each call. Never accept a trusted owner/actor/role context from JSON or rely on auth.uid for this custom auth.

Backend preprocessing ciphertext/verified content can only enter through server-selected fields. Service-only RPC is a trusted backend boundary, but even a direct valid client credential cannot claim owner/another study or widen category projections. SQL SELECT clauses return only allowed category data; identity/contact/text do not leave SQL and then get filtered in JS. Audit identifying/contact/content/export accesses. Audit/version immutability triggers deny UPDATE/DELETE to worker/researchers; retention deletes participant data, not consent definition/version or content-free audit history.

Verification digests are SHA256. Tokens use a domain-separated HMAC of the existing secret, purpose, actual individual identity, study, UUID request and normalized destination; this produces secret pseudorandom tokens and preserves the digest on a legitimate retry. They expire after 30 minutes, are single use and study/participant/pending email/current consent scoped. Invite expiry is server 30 days. Pending-intent reuse, transactional participant/study/destination quotas (including address replacement), at least 60-second cooldown, no more than 5 participant requests/hour, 20 destination requests/hour and 100 study requests/hour. Store content-free attempt counters independent of pending address. Return generic limit results and never echo verification tokens/contact ciphertext to clients. GET/opening URLs cannot verify or enroll.

## Mail and internal worker

`research-mail.mjs` exposes contact encryption/decryption helpers and `runResearchMail(accessStore, researchStore, options)`; internal options use configured key/sender/origin and injected fetch/now for tests. Native Resend POST /emails with persistent provider idempotency key. Store encrypted contact/email body and any raw verification token in outbox only. `RESEARCH_CONTACT_KEY` is required for enrollment/contact; `RESEND_API_KEY`, existing `NOTIFY_FROM` and configured origin required for real dispatch. Tests use only synthetic recipients/provider. Public study data include visible delivery/config errors but no secret/provider payload. Do not send real mail during implementation.

Internal calls use short-lived HMAC token `{k:'research_worker', exp, purpose:'research'}` signed with existing token-secret by the trusted process; accepted only for INTERNAL_ACTIONS, never browser research operations. Internal `recordUsage` uses the actual personal session token instead and is inaccessible through public API.

- `recordUsage`: `{eventId, operation, mode, sourceId, timestamp, durationMs, audience, versions, counts}`. SQL finds only that actor's active verified current-consenting studies with usage enabled; assigns study-local source/session IDs. Successful event allowlist: generate, revise, communicationRound, convert. A session is the first successful AI writing operation in a document/process, including clarification; it is not a page visit. Drafts count AI draft outputs. Revisions count changed manual drafts or AI revision operations with a selected target. Rounds count distinct saved incoming input/extraction, consistent with the existing conversation.rounds; sent snapshots do not double-count. Convert has zero counts and preserves source grouping through its original document ID. Unknown/failed/client-fabricated events never enter public research API. Scope receipts/dedup per event+study. No raw text, instruction, history or original source ID in exported rows.
- `followupSchedule`: `{studyId?}` queues due configured wave/reminder intents once per participant/wave/kind; only current consent/verification/preferences/active date window, optional feedback/update explicitly composed by authorized staff.
- `mailClaim`: `{limit, leaseSeconds}` atomically claims due queued mail and rechecks active state/current consent/withdrawal/preferences. Returns `{messages}` with encrypted worker payload, stable idempotencyKey, createdAt, firstAttemptAt and lease ID. `{messageId, leaseId}` instead revalidates that issued lease immediately before dispatch without issuing another lease/intent. The worker claims one message at a time up to its run limit and obtains a fresh five-minute trusted token per RPC. Expired claims within provider's 24-hour dedup window reuse same intent/key; ambiguous claims beyond window become visible unknown. Withdrawal/erasure cancels unsent and prevents fresh claim; already accepted provider requests cannot be recalled. Content-free issued-attempt evidence permits recording a known in-flight acceptance after cancellation/erasure without reinstating contact or collection.
- `mailComplete`: `{messageId, leaseId, outcome: accepted|retry|blocked|unknown, providerId?, code?}` only current claim holder; immutable attempt/state evidence. accepted means provider acceptance, never claimed delivery. Retry cannot create another key/intent. Unknown requires owner manual known-outcome evidence (`mailResolve`); manual not_sent leaves a blocked resolved record, no automatic requeue.

Just before sending, dispatch rechecks current eligibility through a fresh claim/authorization operation, and does not include untrusted HTML. Provider timeout/lost acknowledgment records uncertainty. Queued welcome is created atomically only after current consent+email verification; verification requests are distinct pre-enrollment contact intents. No welcome from consent preview. Worker retention is run via an owner CLI session or owner dashboard, not a public system bypass endpoint.

## Samples, datasets and integration

Historical text/source metadata and BE GOOD text/source provenance are stored separately. Historical inputs require ownAuthorship=true and minimized=true; encourage only self-authored deidentified messages, never whole third-party conversation archives. Browser may paste or extract TXT/DOCX using existing document readers; binary storage is unnecessary and is not introduced. Optional omission never blocks participation/surveys.

Generated sample `generatedSource`: `{mode:'single', document, proof, draftId}` or `{mode:'continuity', conversationId, entryId}`. U5 injects `resolveGeneratedSample` reusing existing `verifiedSingleDocument` / owned conversation store; backend ignores client claimed model/versions and stores actual verified draft/version content. An unavailable signed source is rejected, with historical participant-declared sources kept explicitly separate. Export contains study-local source IDs, not original conversation/document IDs.

Exports category rights: surveys/usage/historical/generated metadata require view_pseudonymized_data; identities require view_identifiable_data; contacts require BOTH view_identifiable_data/contact_participants. Document text is an explicit `includeContent` option for historical/generated and requires view_document_content plus export_data, approved export category and each sample's separate consent. SQL performs projections and includes dictionary + immutable config/form/system version manifest. Backend adds UTF8 CSV with formula-leading cells neutralized (including whitespace prefixes), plus exact machine JSON. UI downloads JSON/CSV and dictionary/manifest; no optional XLSX dependency. Pseudonyms do not guarantee anonymity of free text; minimized content never described as fully anonymous.

Collection hooks run only after actual successful professional operations using server-authored version/count observations. Research errors do not change/delay the professional result beyond a bounded best-effort local request; no replay queue stores ordinary user data. Existing single transient content, ongoing memory, conversion and general admin permissions remain as implemented. Research pages use dedicated bootstrap/rights and never imply general admin access. Clear/revalidate private DOM/request generations on logout, token/account/study switch, pageshow/focus and denied operations; no cached browser restore of previous authorized data.

U5 integrates gateway/navigation/actual provenance/usage/worker and integrated tests. Root commits only named verified files. Do not mark hosted migration, concurrent revocation, live provider delivery or production permissions verified by a local fixture.

Local prerequisite proof: PGlite 0.5.9 / PostgreSQL 18.6 / pgcrypto 1.4, Node 24.19.0: 33/33 actual ACL/RLS/HMAC/definer/transaction/composite-FK/immutability checks pass. The migration must run unchanged in the fixture and then on an authorized staging database before production approval.
